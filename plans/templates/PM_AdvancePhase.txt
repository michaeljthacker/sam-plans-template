ROLE: PM
TASK: AdvancePhase

Goal: Advance the workflow after the current Phase has been approved by the human. Either set up plans/state.json for the next Phase, or — when this was the last Phase of the milestone — close out the milestone right here, in this same action.

Inputs:
- plans/state.json (routing + context — current phase_id)
- plans/config.json (workflow configuration — read `status_updates`)
- plans/BUILD.md (read `size` from frontmatter — caps how many phases exist)
- plans/MILESTONE.md (phase list — to determine next Phase)
- plans/STATUS.md (current snapshot)
- plans/BACKLOG.md, plans/CHANGELOG.md, plans/thread.md (used only when closing out the milestone)

Instructions:
1) Read plans/state.json to identify the current phase_id.
2) Read plans/BUILD.md frontmatter for `size` (treat missing frontmatter as
   `full` per plans/FORMATS.md). Under `phase-only` and `step-only`, the milestone
   has exactly one phase (P1), so the current phase is ALWAYS the last phase —
   go straight to step 4 (milestone closeout). Skip step 3's lookup in
   plans/MILESTONE.md in that case.

   Note: `size: step-only` should never actually reach this action — the carve-out
   route (Staff.QuickImplement → PM.ThreadMaintenance) bypasses PM.AdvancePhase
   entirely. If you arrive here with `size: step-only`, something has gone wrong
   upstream; route to Human.ResolveBlocker with a blocker explaining the routing
   mismatch.
3) For `full` / `single-milestone` builds, read plans/MILESTONE.md to determine the next Phase:
   - If there is a next Phase in the milestone (e.g., current is P1, next is P2):
     advance to it (steps 5–6).
   - If the current Phase is the LAST Phase in the milestone: the milestone is
     complete — go to step 4.
4) Milestone closeout (inline — last Phase only):
   - Read plans/templates/PM_MilestoneCloseout.txt and carry out its Instructions in
     full as part of THIS action, including its already-closed guard (so a closeout
     can never run twice). Do NOT route to PM.MilestoneCloseout — that action exists
     for direct invocation only.
   - Use the closeout's own STATUS gating and state.json routing (next_action_id,
     context notes, phase_id/step_id/milestone_id), with these differences:
     - last_action.action_id = PM.AdvancePhase
     - last_action.summary names both: e.g. "P3 approved; closed out B1-M2. Next:
       PM.ThreadMaintenance."
   - Then skip steps 5–6.
5) Update plans/STATUS.md (config-gated — next-Phase path only):
   - Read `status_updates` from plans/config.json (default: "pm_only" if missing).
   - If `status_updates = "every_action"`:
     - Refresh the `**Update configuration:**` line at top
     - Now: update Phase ID to the new Phase
     - Recent: "PM.AdvancePhase — advanced from <old Phase> to <new Phase>"
     - Next: "Staff.DraftQuestions for <new Phase>"
   - Otherwise: SKIP. STATUS will lag by one phase under non-`every_action` settings —
     the next end-of-phase PM.StatusUpdate refreshes Now/Next.
6) Update plans/state.json (next-Phase path only):
   - last_action.action_id = PM.AdvancePhase
   - last_action.result = "ok"
   - phase_id = <next Phase ID> (e.g., "P2")
   - step_id = null
   - next_action_id = Staff.DraftQuestions
   - pause_type = "continue"

Constraints:
- Do not implement code.
- Do not modify plans/MILESTONE.md.
- Do not skip Phases — advance sequentially.
- Do not start execution of the next Phase (that is Staff.DraftQuestions' job).
- Do not start the next milestone (that is Principal.MilestonePlan's job, after ThreadMaintenance).

Output:
- Brief summary of the Phase transition (and the milestone closeout, if it happened)
- Exact edits to plans/state.json, plans/STATUS.md, and — on closeout — plans/BACKLOG.md, plans/CHANGELOG.md
